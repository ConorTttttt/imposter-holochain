# Repeatable browser lobbies

## Root cause in the operator alpha

The operator release packages game source `0f7b17592e682a7b7d77e9346528cba69a096cdc`. Its browser hApp has a single host-bound cell and a clone limit of zero. The page pre-fills the cell's `g1.<host>.<id>` deployment seed, requires that same value for both controls, and sends it to `create_lobby` on every click. The native coordinator recovers the existing local Lobby action when the inputs match. It rejects a different configuration and reads the single game index for joins, task processing, and phase. The restricted native role view also requires exactly one Lobby in that index.

The extension records the resulting Lobby action in an irreversible per-DNA, per-agent IndexedDB pin. The same pin holds the one accepted RoleCommit. Closing a browser ends its connection. The signed PlayerJoin action remains, and the RoleCommit fixes the original three seats. The ended round and its roster are therefore recovered on the next connection.

The replacement needs coordinated native, browser, and extension changes. The wire already authenticates the DNA, exact RoleCommit action, seat, sender, recipient, and recipient-key epoch. A native-validated RoleCommit already cites its Lobby and the exact signed joins. Native result validation also needs to bind the reveal and task evidence to the game's Lobby now that several games share a DHT.

## Lobby and round lifecycle

The browser alpha runs one host-bound DNA cell per player. Each browser game has its own Lobby action and code index on that DNA. **Create Lobby** opens the first game and seats the host. **Join Lobby** resolves the exact code to a native-valid Lobby and adds the caller's independently signed PlayerJoin. A duplicate click returns that identity's original join. The host's seat is reserved. When two independently published joins race for the last seat, the coordinator resolves the roster deterministically and the signed RoleCommit fixes the three seats.

**New Game** requires the bound host and the latest completed native game. The first code has 128 random bits. Each successor code incorporates its predecessor's signed GameResult action, so retrying an interrupted creation recovers the same successor. All codes begin with `b1.` and resolve within the installed DNA. A code is a lookup identifier. The host's installed Lair key authorizes creation and round start.

**Open Joined Lobby** recovers an existing seat by exact code, including a completed game. The HWC extension updates its durable selection only after a genuine installed-cell creation or join record. Tabs using the same profile and origin follow that selection. A refresh, profile restart, or **Retry Connection** restores it. Starting a round publishes a new RoleCommit and the **Align Engine Output** task. The host can recover an interrupted task-publication step from the same signed actions.

## Role and result isolation

- Each browser task list, join, RoleCommit, reveal, and result is indexed under its exact Lobby action. Integrity validation checks the link author, target, and parent. Each RoleCommit cites three matching signed joins, including the host. The result validator requires the browser host, the same lobby's commitment and task list, and task evidence from a committed crew member.
- The host makes a fresh private role seal using fresh entropy and the new Lobby action. The unchanged HPKE wire signs and authenticates the exact new RoleCommit, canonical seat, sender, recipient, and recipient-key epoch. The recipient verifies the decrypted Merkle opening against the independently read native root.
- HWC stores a separate immutable commitment pin for each lobby. Selection changes invalidate in-memory requests and receipts for the previous selection. Replay reservations and key epoch floors remain durable at cell scope. After an authenticated lease change, guests request and verify fresh encrypted deliveries. Old ciphertext and old Merkle openings fail against a new commitment even for a returning identity.
- The browser alpha exposes the shared-task round. The desktop clone workflow keeps its existing cell-scoped mechanics. The Firefox Desktop integration applies its existing browser-specific transport patch before the common lobby selection hook.

## Side-by-side Ubuntu deployment

The first rollout requires one new hApp build and the updated Chromium and Firefox HWC extensions. Integrity validation changes the DNA hash. The pinned gateway executable and protocol stay compatible, and the old deployment can keep serving its original game. Each succeeding round on the replacement uses its existing hApp, network seed, HWC identities, gateway, and native authorities.

1. **Stage into separate directories.** Keep `/mnt/holochain/imposter-server/builds/imposter-alpha-1` and its frontend, conductor state, and browser profiles. Use a new path such as `/mnt/holochain/imposter-server/builds/imposter-alpha-repeatable-1`, a separate static root and a fresh authority state directory. Choose a distinct HTTPS frontend origin. HWC binds its Lair identity and single installed app context to the origin. Collect the public key from the actual candidate host at that origin and bind the new package to it. Keep candidate browser profiles and their unpacked extension paths stable across both rounds. Leave the original HWC app installed. Its uninstall operation deletes its Lair key.
2. **Build and verify.** Follow the [operator source pin and package procedure](installed-hwc-browser-alpha.md#operator-build-and-deployment) from the verified integration commit. Use its `build-extension.sh` for Chromium and `build-firefox-extension.sh` for the pinned Firefox Desktop development build. Download or use the retained pinned gateway binary. Run `build.sh` with the candidate host's public key, its host-bound seed, the pinned clean game and HWC checkouts, and the new output directory. Verify the package with `package.py verify` and `sha256sum --check SHA256SUMS`. Record the release commit, DNA hash, hApp digest, manifest checksum and both extension checksums.
3. **Publish the candidate frontend and bring up its authorities.** Copy the operator configuration templates to a protected directory. Put the candidate origin, static root and authority state root into the candidate configs. For the same gateway, reuse the current gateway origin, bootstrap and relay URLs, and its operator-side paths. Add the candidate frontend stanza from `render-proxy` to the existing HTTPS service, retaining the single existing gateway stanza. Run `publish` and `preflight` with the candidate configs and verified release arguments. Use the pinned game's Holochain 0.7.0 Nix shell for `init-native`, then run `run-native --native-admin-ports 33655,33657` on two unused private ports. Run `native-status --native-admin-ports 33655,33657` and verify both full DHT arcs. Keep the original authorities on their existing ports. On a separate authority machine the default ports can also be used.
4. **Admit and verify the two rounds.** With the existing gateway running, use its local `admit` command and candidate release arguments for the candidate host, Chromium guests A and B, and the Firefox guest. Use current verified public keys from each dedicated profile. Confirm the exact installed DNA and authenticated gateway session in every profile. Run Game 1 with the three Chromium profiles through **Ended · Crew wins**. Click **New Game** and record the changed code and initial 1/3 roster. Join as Chromium guest A and Firefox Desktop. Verify three matching native seats and each player's own role before completing **Align Engine Output**. Confirm both games' distinct signed Lobby and RoleCommit actions and crew-win results. Open Game 1 from guest B's existing selection and confirm its original roster.
5. **Keep rollback available.** Until the candidate is accepted, keep sending users to the original origin. If the candidate fails, stop routing users to its origin and keep the original origin and authorities available. Keep candidate state for diagnosis. The static rollback mechanism applies within a single hApp binding. A static swap between these two DNA hashes would leave the installed browser app and served package out of sync.
